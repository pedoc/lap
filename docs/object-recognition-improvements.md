# 对象识别改进任务单

原始照片只读；沿用全局模型和按模型参数，不创建图库模型实例。每阶段验证后独立本地提交，不推送。

- [x] I01：统一语义／人脸／对象的实际推理执行通道，支持公平等待、嵌套调用和等待取消。
- [x] I02：对象任务持久化、原范围恢复、按任务重试失败、清晰的停止与实际设备反馈。
- [x] I03：人工补框、调框、框上就地修改和批量修订。
- [x] I04：新机器结果与人工结果的对照、审核和安全合并。
- [x] I05：可选的重叠切片检测和小目标处理。
- [x] I06：对象索引接入统一搜索，保留命中来源与精确条件语义。
- [x] I07：可选的空闲自动增量处理策略，支持暂停与资源让出。
- [ ] I08：原生窗口交互和大图库长期压测；不将构建／组件渲染测试当作实机验收。

当前阶段：I01–I07。后续各项在本阶段稳定后递进，不能将尚未实施项标记为完成。

## 第一阶段实现边界

- 统一推理通道采用 FIFO 等待，等待期间每 50ms 检查任务取消；同一工作线程的内部嵌套调用可重入，租约禁止跨线程转移。语义、人脸、OCR、对象的实际执行受共同约束，批处理按照片让出；模型初始化也受保护。这是保守单通道，不宣称是多 GPU 并行调度或显存预算器。
- 对象任务保存原范围、模型版本／参数快照和照片清单。选中任务在异步准备前即保存路径、修改时间、大小、方向的元数据摘要；清单生成后恢复只使用剩余原照片。未生成清单的文件夹任务沿原范围重新准备，文件夹身份变化会拒绝恢复，不回退整库。
- 单图识别结果与任务项完成标记同事务提交；进度 JSON 即使在崩溃前未刷新，恢复统计也以逐项账本为准。接续任务复制剩余项及源摘要同事务落盘，二次崩溃也不会把范围扩回原整批。失败重试和未完成恢复互不消耗对方的清单。
- 不自动执行历史任务或切换全局模型。模型或索引参数不匹配时禁止恢复；原参数供查看，用户可切回原配置或另建新任务。显示最近 20 条记录，旧记录不会因此自动删除。
- 文件隐藏、删除、源改变、ID 复用均不会重放为其他照片。旧任务若缺少源快照会明确拒绝恢复，不伪造身份。取消等待可及时退出；已进入单张解码／模型执行时仍需等当前操作结束，未声称实现 ORT 内部强制终止。
- 对象页直接展示最近实际推理后端和回退原因；完成的历史任务不会在每次启动时重新弹出完成浮层，中断任务可以提示恢复。

## 第二阶段（I03）实现边界

- 人工修订改为完整文档保存：前端在图片上直接补框、拖动、拖角调整、就地改类与删除，支持 Ctrl／Shift 多选后的批量改类、确认与删除；后端按整份 `ObjectDocument` 校验并落库，不再要求修订数与机器检测数一一对应。
- 修订保存仍然要求 `revision + sourceKey` 一致，模型或照片变化后拒绝写入；框坐标裁剪到 `[0,1]`，改类后清空原机器分数，人工补框标记为已复核。原始照片只读，修订仅写入本地索引与计数。
- 交互坐标系复用图片变换层（平移／缩放／旋转），以 SVG 的屏幕矩阵反算归一化坐标；仅支持有限拖拽交互，不宣称触控或超高 DPI 下的像素级精度。

## 第三阶段（I04）实现边界

- 审核视图对比「当前人工文档」与「最新机器文档」，以 IoU≥0.5 判定同框；已匹配对象继续保留人工类别与复核状态，仅未匹配的机器框列为候选。
- 候选在侧栏勾选后并入人工文档并整体保存；并入的对象保留机器分数并标记已复核，使用新生成的唯一 ID 避免与原框冲突。未勾选候选不写入，人工独有框保持不变。
- 合并仍复用 `revision + sourceKey` 校验和整份文档校验，模型或照片变化时拒绝写入；不自动删除任何人工框，不宣称跨照片批量合并。

## 第四阶段（I05）实现边界

- 新增按模型参数：`object_tiled`（是否启用）、`object_tile_size`（切片边长）、`object_tile_overlap`（重叠比例）、`object_tile_nms_iou`（跨切片同类去重，默认 0.5）。这些参数计入索引身份，切换后需重新识别；设置页由参数 schema 自动渲染。
- 启用后仅当图片任一边大于切片边长时切分，网格带重叠且末块贴边，不产生额外的窄条切片；每块独立预处理与推理，候选框换算回全图归一化坐标后进行跨切片同类去重。同一切片中的实例继续遵循原模型的 NMS 参数，NMS-free 模型也能去除切片间的重复检出。
- 切片检测通过放大局部区域改善小目标召回，但计算量与切片数成正比；不宣称小目标召回率有保证，也不做逐类先验或像素级小目标专用分支。

## 第五阶段（I06）实现边界

- 统一搜索新增「对象匹配」分组：前端把查询词按本地化名称、模型类别名或类别键解析为当前检测模型的一组类别键，后端以独立 `object_classes` 参数查询，与文件名／备注／OCR 文本查询、视觉语义查询互不污染。
- 对象条件沿用 `count_condition` 的正向语义：以有效行（人工修订优先于机器结果）和 `n >= min` 判定，失败结果不参与；OR 多个类别键时保持逐类参数与精确数量语义。
- 分组按「文本 → 对象 → 视觉」去重，命中来源在分组层面可见；不宣称跨模型语义合并，也不把对象命中冒充为文件名或 OCR 命中。

## 第六阶段（I07）实现边界

- 对象页新增可选空闲策略：默认关闭，可设置空闲秒数、每批照片数和文件夹范围。仅当策略启用、未暂停、图库已建立对象索引、全局模型已安装且没有运行中任务时才启动，单批结束后重新回到空闲等待。
- 任意窗口的交互活动都会请求自动任务让出；正在解码或推理的单张照片需要退出当前操作后才能启动手动任务。手动停止自动任务会暂停策略，模型缺失或致命错误也会暂停并显示原因，不会自动重试失败照片。
- 自动任务只处理尚未完成的照片，沿用当前全局模型与参数快照，不下载模型、不切换模型、不绕过手动任务的范围与修订保护。轮询与启动仍受统一推理通道约束。

## 审查修复（201f1bee 之后的改动）

- 原图编辑的框、手柄和工具栏恢复鼠标命中，手柄使用框内坐标；退出编辑和卸载图层时释放拖动监听器。
- 编辑失效判断采用后端模型配置、源摘要、修订版本与真实变更事件，取消跨组件本地计数比较；重建详情栏不会让未变化的数据立即过期。
- 普通修订和候选合并保留不完整标记，后端同样阻止将已有截断结果误写成完整结果；精确数量与不存在条件继续排除这些照片。
- 空闲调度跳过没有待处理照片的图库；后端也在校验权重、创建持久化任务之前检查目标是否为空。注册自动任务时持有任务锁重新验证策略，执行检查点持续验证空闲状态和策略版本；策略变化会让当前自动任务退出。
- 自动任务的文件夹范围与批次上限写入恢复请求，准备阶段中断后也不会丢失范围或扩大批次。
- RF-DETR 的 DirectML 兼容改写仅用于已验证的权重 SHA-256；导入的其他权重保持其原始算子语义。
- 搜索测试显式使用夹具的模型配置，不读取用户当前启用模型来解释测试数据库。

本轮验证：前端全量 478 项测试通过，前端构建和 Rust 编译检查通过；对象存储、调度、恢复、适配器、参数和运行时共 53 项 Rust 单元测试通过。隔离样片上的 RF-DETR CPU、DirectML、DirectML 切片三种场景均通过；GPU profiling 分别记录到 24、60 个 DirectML 执行事件。

I08 仍待后续阶段。原生窗口交互和大图库长期性能必须单独验收。

## 启动阻塞修复（2026-10-18）

- 对运行中进程进行线程栈采样，确认共享后台线程池的 512 个线程全部占用：510 个文件夹同步任务等待相册锁，一个语义任务等待 OCR 让出推理通道，而 OCR 正等待同一线程池里的图片解码。对象启动请求无法进入工作线程，数据库因此没有新增任务；页面上的「意外中断 0/0」来自上次退出前的历史任务，不是本次 GPU 报错。
- 增量缩略图与语义任务改为在异步侧等待并发许可，最多两个任务进入后台线程池。许可由真实工作线程持有，取消异步等待者不会提前释放；文件夹扫描也移到后台执行，避免阻塞异步执行器。
- OCR、对象和区域分析复用已有工作线程直接解码；异步编辑入口继续离开异步执行器后解码。两条路径共用方向／预览逻辑，不修改原图。
- 排队任务携带原图库标识，执行时持图库读锁校验，图库切换后不能把旧文件 ID 写入新数据库。语义生成复用已持有的图库锁，不递归加锁。
- 对象启动成功即显示返回的运行状态，停止成功即显示停止中；统计与历史刷新不再占用操作按钮，旧刷新结果不能覆盖停止状态。
- 新增 600 个排队任务下的线程池容量回归，执行真实任务日志注册与图片加载；另覆盖许可取消生命周期、八方向解码一致性，以及启动／停止遇到缓慢刷新、启动失败和切库的前端行为。这是隔离的并发回归，不代表 I08 的真实大图库长测已完成。

本轮验证：前端全量 481 项、相关 Rust 回归 64 项通过，前端生产构建及 `cargo check --locked` 通过。新编译的 Rust 测试程序再次通过 RF-DETR CPU 和 DirectML 样片验证，后者记录到 24 个 DirectML 执行事件。`cargo fmt --check` 仍报告 `build.rs` 等文件的既有格式差异，未为此批量改写无关源码；测试链接另有不阻断运行的 `LNK4098` 警告。

## 清单准备性能与阶段进度（2026-10-19）

- 新任务已注册，但在 `plan_sources → media::source_optional_on` 阶段长时间停留。现场线程栈显示 SQLite 正在逐张读取源信息，并非再次耗尽线程池，也尚未加载模型。原单图查询每次都重建整库 Live Photo 伴随文件列表，并扫描所有排除文件夹；现场每次约 45–50ms，万张照片会累积成分钟级等待。
- 批量统计仍复用一次性集合查询；单图元数据／写入校验改为索引点查和单文件夹可见性判断。复用已有的 Live Photo 关系索引并缓存预编译语句，不缓存行内容，不改变隐藏、回收站、RAW、文件夹排除和源摘要规则，也不预读原始照片。
- 状态区分「收集照片、准备任务清单、等待推理资源、加载模型、识别」。准备阶段有独立的 `prepared / total`，不知道总数及加载模型时使用不定进度，不再把准备数量当作识别成功数量或一直显示 `0/0`。
- 轻量进度事件直接更新当前图库／任务，通知时不持任务状态锁。准备通知按 150ms 节流，首尾及阶段切换立即推送。较早的查询、旧任务事件、延迟的启动回复不能覆盖较新的进度或撤销停止状态。准备计划仍原子提交；准备取消会回滚未完成清单，不留下半份可恢复账本。
- 前端全量 485 项、相关 Rust 回归 69 项、前端生产构建及 `cargo check --locked` 通过。实际生产准备函数在同规模合成图库中生成 11,470 条任务账本约 229ms；另以只读连接核对现场图库全部 11,470 条源元数据，点查约 675ms，源摘要和尺寸与原批量可见性查询完全一致。增加 SQLite VM 步数／索引计划断言，防止点查退回全库扫描；这些耗时不是模型识别整库所需的时间。

原生窗口的整库长期运行仍属于 I08，不能用元数据性能测试或组件渲染代替完整验收。

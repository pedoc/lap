# 将 Lap 能力暴露给 Agent

状态：设计提案，尚未实现。更新日期：2026-10-26。本稿替代此前的多层上下文编排方案。

## 结论

将 Lap 现有业务封装为一组工具（Lap Tools）。内置 Agent 通过模型的 function calling 使用这些工具；需要外部 Agent 接入时，用 MCP 暴露同一批工具。工具的业务实现只有一份，位于 Rust 后端。

```text
Lap 内置 Agent ── function calling 适配 ──┐
                                        ├── Lap Tools ── 现有 Rust 业务服务
外部 Agent ── MCP 适配（按需增加）────────┘
```

先确定工具接口和调用闭环即可。权限、分页、取消和结果记录沿现有业务扩展，不提前建立独立的计划、证据、快照或权限框架。

## 1. 用什么形式暴露

| 使用者 | 调用形式 | 说明 |
| --- | --- | --- |
| Lap 内置 Agent | Function calling，应用执行本地工具函数 | 不需要启动本地网络服务；Lap 将工具结果回传用户配置的模型 |
| 外部 Agent 客户端 | MCP Server | 提供标准工具发现与调用，复用相同函数 |
| 普通应用集成 | 有明确需求时增加 HTTP API | 使用相同函数；当前不单独建设另一套接口 |

Function calling 负责模型提出工具调用、应用执行并回传结果。MCP 负责 Agent 客户端发现和调用应用提供的工具。二者可以配合使用，不要求内部调用先经过 MCP 网络服务。

若产品目标明确优先服务外部 Agent，则优先建设 MCP 出口；目前的内置聊天需求可以直接从 function calling 接入。

## 2. 工具最小定义

每个工具只需要名称、用途说明、参数 JSON Schema 和 Rust handler；有需要时补结果 schema。模型侧和 MCP 侧的描述从同一份定义生成。

执行时传入当前图库、可访问媒体范围、读写许可和取消信号。handler 调用现有领域服务，不将全部 Tauri 命令、SQL 或本地文件系统直接开放。

建议先确定这些业务工具，具体接入顺序另行安排：

| 工具 | 参数示例 | 返回／行为 |
| --- | --- | --- |
| `search_media` | 查询词、日期／人物／标签条件、数量上限 | 通过现有结构化或向量检索返回媒体引用与摘要 |
| `get_media_info` | 媒体 IDs、所需字段 | 文件名、标题、标签、EXIF、人物、人脸／对象区域、OCR、已有分析等获准资料 |
| `get_media_content` | 媒体 ID、区域或视频区间 | 获准的缩略图、图片或采样帧；由模型协议适配器编码 |
| `analyze_media` | 媒体 IDs、识别任务类型 | 复用已有识别／理解任务，返回任务状态或引用 |
| `propose_metadata` | 媒体 IDs、标题／说明／标签建议 | 进入现有资料预览和确认写回流程 |

读取已有结果与运行新识别使用不同工具。`get_media_info` 可按字段查询，例如只取 `people`，不必为每类元数据另建一套聊天功能。

## 3. 一个完整例子

用户引用图片后问：“画面里都有哪些人？”

1. Agent 获得问题、当前媒体引用和可用工具描述。
2. 模型请求 `get_media_info(file_ids=[42], fields=["people"])`。
3. Rust 读取 Lap 已有人脸／人物归属，返回名称、区域、确认／建议状态；未命名和未识别结果明确标记。
4. Agent 将工具结果交给模型，生成带媒体来源的回答。
5. 如需查看画面，再调用获准的 `get_media_content`；如需新识别，则使用独立的分析工具。

“查询照片”“解释拍摄参数”“依据对象和人物生成标题”都可以通过组合这些工具完成。UI 中的上下文选择可直接限制允许返回的字段／工具，或显式预先读取资料，仍复用同一个 handler。

## 4. 保留几条必要规则

- 默认围绕当前引用／选择操作；全库检索使用明确的图库范围。工具参数不能扩大执行端给定的范围。
- 返回有限、结构化的业务资料，附媒体 ID、区域／视频时间及必要状态。人物名称采用已有标注；原路径、密钥和原始向量不随资料返回。
- 修改走现有预览确认和版本检查；新增计算沿用现有任务机制。读取许可不自动启动识别或确认写入。
- 内置 Agent 负责完整的“调用模型 → 执行工具 → 返回结果 → 继续回答”循环，保留取消、数量／时间限制和调用记录。部分流式参数不执行，普通回答文本不当作工具指令。
- 工具结果进入后续对话后仍可能被再次发送，界面应明确历史范围；切换接收服务或希望停止分享此前资料时，可开始新的模型上下文，保留本地历史。

这些是工具执行入口的基本约束，不单独发展为新的平台。

## 5. 如何接当前 Lap

工具放在 Rust 后端，复用媒体查询、人物、对象、OCR、EXIF、Embedding 检索和资料采用服务。Vue 继续负责聊天界面、媒体引用、模型选择及必要的操作展示。

当前 `chat.rs` 已有会话和流式反馈，`client.rs` 已有模型 SDK 适配。后续在此补工具定义、调用执行和结果回传即可；工具 schema 与 handler 保持独立，便于 MCP 复用。

模型适配器按实际模型支持的协议处理 function calling，不能因为 API 地址兼容 OpenAI 就假设所有模型都支持工具。缺少工具能力的模型仍可使用应用预先读取资料的确定流程。

MCP 出口可复用官方 Rust SDK `rmcp`。连接已经运行的 Lap 时，建议按需提供仅本机监听的 Streamable HTTP，并设置认证与 Origin 检查；需要 stdio 的客户端可使用桥接进程。外部客户端接入与内置 Agent 的本地工具执行分别处理，不要求云端模型能直接访问用户电脑的端口。

本轮只调整设计文档，未实现工具循环、MCP 服务或具体工具。
